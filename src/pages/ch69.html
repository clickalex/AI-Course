Serve & demo your model

A model on your laptop helps one person. Wrap it in an API and a demo UI and it helps the world. Build a FastAPI endpoint with validation, test it with curl, slap on a Streamlit/Gradio UI, and ship it — the full “model to URL” path in one chapter.

1. FastAPI in 30 lines (your model, now a URL)

Diagram 69.1 — Request → validation → preloaded model → JSON. Load the model once at startup, never per request.
# app.py — pip install fastapi uvicorn pydantic
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()
model = load_model_once("sentiment.pt")   # startup, NOT per request

class Review(BaseModel):
    text: str                              # validated automatically

@app.post("/predict")
def predict(r: Review):
    label = model.predict(r.text)          # your sklearn/torch model
    return {"label": label}

# run: uvicorn app:app --reload
# docs: http://127.0.0.1:8000/docs (free Swagger UI!)
# test it from another terminal
curl -X POST http://127.0.0.1:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"text": "loved the thali, will return!"}'
Snapshot 69.1 — FastAPI’s free Swagger UI at /docs: every endpoint documented and clickable. Green POST, “Try it out”, instant 200 response.

# demo.py — pip install streamlit, run: streamlit run demo.py
import streamlit as st
import requests

st.title("Thali review sentiment")
text = st.text_area("Paste a review")
if st.button("Predict") and text:
    r = requests.post("http://127.0.0.1:8000/predict",
                      json={"text": text}).json()
    st.success(f"Prediction: {r['label']}")

3. From laptop to link (ship checklist)

  1. Pin + freeze: requirements.txt with versions; test in a fresh venv (Ch 70).
  2. Cheap first: Gradio share link or HF Space for feedback; Docker + cloud VM when real users arrive (Ch 44).
  3. Guard the endpoint: input length limits, rate limiting, no stack traces to clients, API key for anything non-public.
  4. Log predictions: inputs + outputs + latency → your future eval set and drift monitor (Ch 43).

Demo-driven disasters

Loading a 7B model per request, exposing /docs with no auth on the public internet, and returning raw tracebacks (which leak paths and package versions) are the classic trio. Load once, bind admin routes to localhost, validate and truncate every input — the checklist above exists because each item has bitten someone.

Short notes

FastAPI: model loaded once, Pydantic validates, uvicorn serves, /docs free. Test with curl. Streamlit for data apps, Gradio for model playgrounds, HF Spaces for free hosting, FastAPI + Docker for production. Ship: pin deps, cheap-first hosting, guard inputs, log predictions for evals.

Point notes

  • Load model once.
  • Pydantic validates free.
  • curl before UI.
  • Demo cheap, scale later.
  • Log every prediction.

Practice questions

P1. Your /predict takes 9s on first call, 80ms after. Explain + fix.

Cold start: model (or tokenizer/weights) loads lazily inside the endpoint on first request. Fix: load at startup (module scope or lifespan event); warm up with one dummy predict during deploy; add a /health endpoint that reports model-loaded status so the load balancer waits. Bonus: log load time as a deploy metric.

Self-mark:

P2. Someone pastes a 2MB review and your demo OOMs. Harden the endpoint (4 guards).

(1) Pydantic max_length on text (e.g. 2000 chars) → 422 on abuse. (2) Request timeout + max body size at server level. (3) Truncate-then-infer with a logged warning, or chunk long inputs. (4) Rate limit per IP/key. Also: return generic 500s (tracebacks stay server-side) and alert on repeated 422s — could be fuzzing.
