Kubernetes for ML workloads

One GPU VM is a pet; fifty is a stampede. Kubernetes turns stampedes into cattle: declarative jobs, GPU scheduling, autoscaling, and self-healing. Learn the 20% of K8s that runs 80% of ML — pods, jobs, quotas, and when to walk away.

2. GPUs on K8s (requests, quotas, sharing)

# train-job.yaml — one GPU, 4 CPU, retry twice, die politely in 24h
apiVersion: batch/v1
kind: Job
metadata:
  name: train-bert-v3
spec:
  backoffLimit: 2
  activeDeadlineSeconds: 86400
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: trainer
        image: registry/img:ml-2.4.1
        command: ["python", "train.py", "--config", "bert-v3.yaml"]
        resources:
          requests: {nvidia.com/gpu: 1, memory: 16Gi, cpu: 4}
          limits:   {nvidia.com/gpu: 1, memory: 24Gi}
        volumeMounts:
        - {mountPath: /data, name: data}
      volumes:
      - name: data
        persistentVolumeClaim: {claimName: ml-data}
# daily driver commands (alias k=kubectl, thank me later)
kubectl apply -f train-job.yaml
kubectl get pods -w                       # watch scheduling
kubectl logs -f job/train-bert-v3         # follow training logs
kubectl describe pod <name>            # why Pending? (events!)
kubectl top pods                          # CPU/RAM per pod
Snapshot 74.1 — kubectl get pods: API serving on 1 GPU, training running on another. Logs stream with -f; the quota comment keeps teams honest.

3. When K8s (and when a VM)

  1. Choose K8s when: multiple models/teams share GPUs, traffic needs autoscaling (HPA/VPA + cluster-autoscaler), or jobs must self-heal overnight. Namespaces + quotas stop teams eating each other’s GPUs.
  2. Choose a VM when: one model, one team, steady traffic — a single GPU box with Docker + systemd wins on simplicity for months (Ch 44).
  3. Costs to budget: control-plane fees, idle GPU requests (requests ≠ usage — rightsizing matters), storage/egress, and engineer-hours learning YAML. FinOps labels per team/model from day one.
  4. ML platforms on top: Kubeflow, Flyte, Ray on K8s add pipelines + experiment tracking — adopt when raw Jobs drown you in YAML, not before.

Pending-pod purgatory

“0/3 nodes available: insufficient nvidia.com/gpu” means your request exceeds the cluster — kubectl describe the pod and READ THE EVENTS. Fix order: lower the request, add a node pool / autoscaler, set quotas so one team can’t starve others, and never latest-tag training images (unreproducible reruns are undebuggable incidents).

Short notes

Six objects: Pod, Deployment (serve), Job/CronJob (train), Service/Ingress (route), PVC/Secrets (state). GPUs via nvidia.com/gpu requests + quotas; debug with describe + events; logs -f for training. K8s for shared/autoscaled/self-healing fleets; a VM for one model + one team. Label costs, pin images, rightsizing never ends.

Practice questions

P1. Two teams share 8 GPUs; team A’s jobs starve team B. Fix with K8s primitives.

Namespaces per team + ResourceQuotas (e.g. 4 GPU each, burstable with limits) + LimitRanges for sane defaults. Add priority classes (prod serving > experiments) with preemption, and FinOps labels for chargeback. Verify: describe quota usage weekly; alert at 90%. Social fix: shared calendar for big sweeps — primitives plus manners.

Self-mark:

P2. Nightly batch inference must finish by 6am or page someone. Design it.

CronJob at 1am (buffer for retries): parallelism over shards, backoffLimit 3, activeDeadlineSeconds before 6am, PodDisruptionBudget for the serving tier so batch doesn’t evict prod. Liveness: success metric → alert if no successful Job by 5:30am. Logs to central store; model image pinned; input snapshot versioned so reruns reproduce.

Self-mark:

P3. Your inference Deployment OOMs at traffic peaks but idles at night. Rightsize it.

HPA on custom metric (queue depth / p99 latency, not just CPU) with min/max replicas; VPA in recommendation mode first to fix requests vs usage; PodDisruptionBudget + rolling updates for safe churn; cluster-autoscaler for node capacity; scale-to-near-zero for dev namespaces. Review weekly: requests should hug the p90 of actual usage.
